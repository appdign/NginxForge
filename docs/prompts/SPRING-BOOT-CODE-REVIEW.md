# Spring Boot 코드 전용 점검·수정 프롬프트

아래 내용을 별도의 Spring Boot 애플리케이션 저장소에 전달합니다.

```text
현재 Spring Boot 백엔드의 코드에서 발생하는 보안 문제를 점검하고 수정·테스트해줘.
AGENTS.md, Java/Spring Boot/Security 버전, MVC/WebFlux, DB/인증 구조를 먼저 확인해줘.
기존 정상 기능을 유지하고 사용하지 않는 기능은 근거와 함께 미대상 처리해줘.

범위:
- NGINX의 TLS/HTTPS, 응답 보안 헤더, CORS, 쿠키 플래그, 요청 크기/IP 빈도 제한,
  경로/IP 차단, 캐시 정책, 프록시 전달 헤더 설정은 코드 점검에서 제외해줘.
- 세션 TTL, PasswordEncoder 정책, SecurityFilterChain/메소드 보안 활성화,
  표준 JWT 검증 설정, Actuator 노출, 에러 표시, multipart 한도, 프로파일,
  비밀값 주입, 의존성/서비스 계정/OS 권한 등은 프레임워크·운영 설정 표로 분리해줘.
  Java @Bean/보안 DSL도 설정이면 같은 원칙이야. NGINX가 대신할 수 있다고 표시하지 마.
- 기존 프레임워크 기능을 사용할 수 있으면 보안 기능을 직접 재구현하지 마.
- 실제 인증·인가·저장·응답·감사 로직의 결함은 코드 수정 대상이야.

1. 객체별 인가와 데이터 격리
[ ] 조회·목록·검색·수정·삭제·다운로드에서 사용자/역할/소유자/테넌트 권한을 확인하는가?
[ ] ID나 테넌트 식별자를 바꿔 다른 사용자 자료에 접근할 수 없는가?
[ ] 백그라운드 작업·다른 서비스 호출 경로에서도 필요한 인가가 누락되지 않는가?
[ ] 권한·소유자·테넌트·가격 등 보호 필드를 클라이언트 입력으로 변경할 수 없는가?
[ ] DTO와 명시적 매핑으로 허용한 입력만 처리하고 엔티티를 그대로 노출하지 않는가?

2. 입력과 외부 호출
[ ] 실제 컨트롤러/서비스 경로에서 타입·길이·범위 및 업무 규칙 검증이 실행되는가?
[ ] SQL/JPQL/native query에 입력 문자열을 연결하지 않고 파라미터 바인딩을 사용하는가?
[ ] 입력값을 명령어·템플릿·파일 경로·동적 코드로 직접 실행하지 않는가?
[ ] 외부 URL 가져오기 기능이 있다면 목적지·리다이렉트·주소 해석 과정의 SSRF 우회를 방어하는가?
[ ] 실제로 불신 데이터를 처리하는 파서·압축 해제·변환 로직에 자원 고갈 우회가 없는가?

3. 파일과 업무별 용량 통제
[ ] 파일별 소유권과 업로드·다운로드·삭제 권한을 서버에서 검사하는가?
[ ] 파일 저장 키를 서버에서 생성하고 사용자 파일명을 내부 경로로 사용하지 않는가?
[ ] 확장자/Content-Type 하나만 믿지 않고 필요한 실제 형식·내용 검증을 수행하는가?
[ ] 경로 이탈·덮어쓰기·링크/경쟁조건·압축 해제 경로 우회를 방어하는가?
[ ] 실패/중단/검사 거부 시 임시 파일과 DB 상태를 일관되게 정리하는가?
[ ] 계정별 저장 용량·다운로드 총량 등 업무 할당량을 동시 요청에도 일관되게 적용하는가?
[ ] Range·재시도·이어받기·서명 URL로 인가나 총량 정책을 우회할 수 없는가?
    NGINX의 요청 크기/전송 속도 제한을 이 업무 로직의 대체 수단으로 보지 마.

4. 인증 흐름·오류·감사 로직
[ ] 직접 구현한 초기 계정/초대/비밀번호 재설정 흐름에 공통 비밀번호나 재사용 우회가 없는가?
[ ] 직접 발급하는 재설정/초대 토큰의 생성·저장·만료·일회성 소비가 안전하고 원자적인가?
[ ] 로그아웃·비밀번호/권한 변경·계정 비활성화 코드가 필요한 인증 무효화와 연결되는가?
[ ] 사용자 정의 인증/CSRF 필터가 있다면 우회·실패 처리 결함이 없는가?
    표준 기능으로 해결되면 새 필터를 만들지 말고 설정 항목으로 이동해줘.
[ ] 커스텀 예외 처리·응답 DTO에 SQL·비밀값·내부 경로·타 사용자 데이터가 노출되지 않는가?
[ ] 오류를 성공 200 응답으로 숨기거나 외부 오류 본문을 그대로 반환하지 않는가?
[ ] 직접 작성한 로그/감사 이벤트에 토큰·비밀번호·민감 본문이 들어가지 않는가?

5. 검증
[ ] 비로그인/일반 사용자/관리자/타 소유자/타 테넌트 시나리오를 검증했는가?
[ ] 동시 요청, 토큰 재사용, 악성 파일/경로, 오류/정상 흐름을 기존 테스트로 검증했는가?
[ ] MVC/WebFlux에 맞는 테스트에서 실제 적용된 인증·인가 경로를 검증했는가?

결과:
항목 | 조치 완료/미흡/미대상/확인불가 | 변경 파일·위치 | 테스트 증거 | 잔여 작업

NGINX 설정 / Spring·인증 서버 설정 / 빌드·배포·DB·OS 설정은 별도 표에 기록해줘.
프레임워크 설정의 미확인을 코드 조치 완료로 대체하지 말고 실제 적용 상태를 표시해줘.
테스트하지 않은 환경·운영 변경은 완료로 표시하지 마.
KISA 항목과 일반 애플리케이션 보안 요구사항을 구분해줘.
```
